この回の要点

2. Midnight が Cardano から読むもの、そして db-sync の重さ

必要なのはメガバイト。用意させられているのは 700 ギガバイト。

Santiago Carmuega はまず、Midnight のノードが Cardano から何を読んでいるかを整理します。Cardano で起きること全部ではなく、コンセンサスに必要な薄い一枚だけだ、という説明です。挙げられたのは 4 つ。

  • 特定のスクリプトアドレスにある UTXO
  • 各ステークプールが持つステークの量
  • チェーンのノンス
  • チェーンの先頭（tip）がどこか

補足「なぜ Midnight が Cardano を読むのか」は動画では前提として飛ばされています。Midnight は Cardano のパートナーチェーン（Cardano の SPO とステークを借りて動く別チェーン）で、誰がブロックを作る番かを決めるのに Cardano 側のステークとノンスを使い、Cardano 上のスクリプトアドレスに置かれた登録情報を読みます。だから「薄い一枚」がコンセンサスに直結する、という話です。

ところが現状、この一枚を読むために Midnight のオペレーターに求められているのは cardano-db-sync です。これは Cardano の全データを PostgreSQL に流し込む索引ツールで、自らも「汎用のインデクサ」と名乗っている、と Santiago は言います。エクスプローラにもウォレットにも取引所の分析にも使える代わりに、すべてを保存する。動かすには 3 つが要ります。

  • PostgreSQL のインスタンス
  • db-sync 本体（PostgreSQL に書き込み続ける更新処理）
  • それと同じ場所に置く cardano-node

3 つを足し上げた目安として挙げられた数字が、RAM 約 64GB、ディスク約 700GB、CPU 5〜8 コアです。しかも同期の確認、部品どうしの連携、PostgreSQL のチューニング、遅れないようにする作業が「ある意味フルタイムの仕事」になる、と述べられました。司会も、db-sync の同期が終わったと思ったら Midnight 用のデータベースにもう一度索引を作り直す必要があり、「ノードを立ち上げるだけなのに、思ったよりずっと長くかかる」と実体験を重ねています。

Santiago は 2 度、「これは db-sync への批判ではない」と断っています。すばらしいソフトウェアだが、Midnight が要るものとの間に摩擦がある、という言い方です。

左の数字は Santiago Carmuega が「だいたい」として挙げたもので、右の Dolos の数字も本人の説明です。補足動画の前日に提出された問題提起 MPS-0038 の文書では、db-sync 側の要件として 700GB の SSD に加えて 60,000 IOPS、mainnet の同期に約 2 日、と書かれています。

補足RAM の要件は資料によって食い違います。MPS-0038 の文書は「Midnight の公式ドキュメントは 32GB、db-sync の README は 64GB を推奨」と両方を並べており、動画で Santiago が使ったのは 64GB のほうです。どちらが実運用の正解かは、動画でも文書でも決着していません。

3. Dolos — 1 バイナリの「データノード」

ブロックは作らない、検証もしない。読むことだけに特化したノード。

Santiago は Dolos を Cardano の「データノード」と呼んでいるので、以下もその言葉で書きます。

データノード 動画の中の言葉

ブロックを生成せず、ブロックの検証もせず、ネットワークの中継もしない。Cardano のリレーのネットワークに直接つないで、台帳の自分用のコピーを組み込みのデータベースに保持し、それを読み出す API を同じプロセスの中で提供する。補足ふつうの Cardano ノードは「合意に参加する」役と「データを持つ」役を兼ねています。Dolos は後者だけを切り出したもので、TxPipe の公式ドキュメントも「ブロック生成には対応しないし、今後もしない」と明記しています。

動画で挙げられた特徴は 4 つです。

  • API がひととおり入っている。Blockfrost とまったく同じ見た目のエンドポイント、UTxO RPC（UTXO 型チェーン向けの gRPC ベースの API）、Kupo 互換のインターフェース、そして Ogmios を上に載せて使う経路。「Blockfrost に問い合わせるのと同じように Dolos に問い合わせられる」。
  • 資源が小さい。RAM 約 3GB、CPU 0.5 コアで「十分快適」。
  • 履歴を切り詰められる。Byron から今までを全部持つ必要はなく、「数日」「6 週間」など残す期間を設定で決める。この窓は先頭に追随し、古い分は捨てられていく。Santiago は「私にとってはここがいちばん面白い」と言っています。
  • 隣にノードが要らない。信頼できる情報源は必要だが、db-sync のように同じ場所に cardano-node を置く必要はない。SPO ならすでに動かしているリレーに Dolos を向ければよい。

補足Kupo と Ogmios は、Cardano の DApp 開発でよく組み合わせて使われる 2 つの補助ツールです。Kupo は「このアドレスに今ある UTXO」を素早く引くための索引、Ogmios はノードと WebSocket でやり取りするための橋渡し。司会が「昔の testnet では SPO が Kupo と Ogmios の接続を用意しなければならなかった」と振り返っているのは、Midnight のバリデータの初期の手順にこの 2 つが入っていたためです。

専門用語が多い節です — かみくだいた説明を開く

補足以下はこちらで足した解説です。動画の発言ではありません。

そもそも「履歴を切り詰める」とは

Cardano のチェーンは 2017 年（Byron 期）から今まで、すべてのブロックがつながっています。db-sync はその全部を索引にするので 700GB になる。Dolos は「直近 1 日分」「直近 6 週間分」のように残す幅を決めて、それより古いものを消すことができます。動画ではこれを「スライディングウィンドウ」と呼んでいます。窓が先頭とともに動く、という意味です。

なぜ Midnight には数日で足りるのか

動画で「安定性ウィンドウ（stability window）が気になるなら数日分」と言われています。Cardano では、ある深さより古いブロックは覆らない（巻き戻しが起きない）と見なされる期間があり、それが安定性ウィンドウです。Midnight が読みたいのは「確定した最近の状態」なので、確定に必要な幅さえ残っていれば、それより古い履歴は読まなくてよい、という理屈です。

身近なものへのたとえ

新聞の縮刷版を全巻そろえておく（db-sync）のと、今週の分だけ手元に置いて古いものは捨てる（Dolos）の違いです。「今日の記事を読む」だけなら後者で足ります。

この動画では分からないこと

Midnight のノードに実際に必要な最小の幅が何日なのか、そして「6 週間」がどこから出た数字なのかは説明されていません。「Midnight は安定性ウィンドウを気にしていると知っている」という一言で、次の話題に移っています。

用途は Midnight に限らない、という点も両者が強調しています。司会は Blockfrost の API に頼っている開発者が多いことを挙げ、Santiago は「いくつかのチームは Dolos に組み込まれた Blockfrost 互換 API を外部に公開して、本番の mainnet のエンドポイントとして直接叩いている」と述べました。高可用性やエッジへの分散が要るならサービスプロバイダーに払う理由はあるが、自分のインフラを自分で持ちたいなら Dolos は「本当に面白い選択肢」だ、という整理です。Dolos はオープンソースで、複数のチームからの貢献を受けているとも述べられました。

4. 「Dolos を入れてくれ」ではなく「境界を決めてくれ」

問題提起は解決策を書かない。まず仕様と適合テストを求める。

司会が、TxPipe が Midnight の改善提案のリポジトリに問題提起を出したことに触れます。Midnight には Midnight Improvement Proposal（MIP）という提案の仕組みがあり、その前段が問題提起（Midnight Problem Statement、MPS）です。

MPS と MIP 動画の中の言葉

Santiago の説明では、MPS は「何が改善できると思うか」だけを述べ、どう改善するかは書かない。それが通ってから、解決策を書く MIP を出す。Santiago 自身「このプロセスは初めてで、これが最初の 1 本」と断っています。補足Cardano の CIP（Cardano Improvement Proposal）にも同じ「問題提起（CPS）→ 提案（CIP）」の 2 段構えがあり、Midnight の仕組みはそれを踏襲したものです。

問題提起の中身は、この動画の前半で語られたことそのもの、と司会も Santiago も言っています。ただし求めているものは Dolos の採用ではありません。Santiago の言葉では「むしろ逆で、問題提起では解決策の話はしていない」。求めているのは次の 2 つです。

  • Midnight ノードと「Cardano オブザーバー」（Cardano を読む部品が何であれ）の間のインターフェースを記述する、明確な契約——きちんと定義された仕様
  • どのオブザーバーのバックエンドでも要求事項を満たしているかを確かめられる、適合テストのスイート

この境界が決まれば「この SPO は db-sync の代わりに別の解を動かしたい」と考え始められる。それは Dolos かもしれないし、ほかのバックエンドかもしれない。ベンダーが入ってきて自分のバックエンドを提供できるようにするのが狙いだ、と述べられました。そのうえで、問題提起が承認されたら後半として改善提案を出し、「このインターフェースに Dolos を通してみてはどうか」と提案して適合テストを満たす努力をする、と予定を語っています。

Santiago Carmuega の説明を 2 段に並べたものです。「まだドラフト」と本人が言っているとおり、マージは「議論の場に載った」ことを意味し、承認ではありません。

補足問題提起は MPS-0038「Operational Cost of Cardano Observation」として 2026 年 9 月 2 日、つまり動画の当日に Midnight の改善提案リポジトリへマージされています（ステータスは Draft）。文書には動画にない数字も入っていて、Midnight の問い合わせが触るのは db-sync の約 80 テーブルのうち 11 だけ、という記述があります。求めている成果物は「観測の契約の仕様」「midnight-node での差し替え可能なデータソース」「適合テストのスイート」の 3 つで、動画の説明と一致します。

補足動画公開後の結果として一つ。同じリポジトリには 2026 年 3 月から、別のチームが Acropolis という Rust 製ノードで db-sync を置き換える改善提案を出していましたが、コミット署名の検証が通らないまま 9 月 9 日にクローズされています。動画ではこの提案には触れられていません。「db-sync を軽くしたい」という要望が TxPipe だけのものではない、という背景です。

5. デモ — 同期の 3 つの入り口と、誰を信じるか

対話式の初期設定は 1 分。いちばん重いのは、最初のデータをどこから持ってくるか。

Santiago は画面を共有し、Dolos の初期設定を対話式に進めました。聞かれるのは、つなぐネットワーク（mainnet）、Genesis ファイルを自分で用意するか、データを引くリレー（Demeter のリレーか Cardano Foundation のリレー）、残す履歴の幅（全部、1 日、1 週間、1 か月）、公開する API（UTxO RPC、Blockfrost 互換、Kupo 互換）、ほかのノードのリレーになるか。最初はすでにインスタンスがあるフォルダで実行してエラーになり、別のフォルダでやり直しています。

最後に聞かれる「どこから同期するか」が、Santiago が「本当に重い部分」と呼ぶところです。3 つの選択肢が示されました。

  • TxPipe のスナップショット。数分で現在の状態をダウンロードする。Santiago はこれを「trust me bro」と呼んでいます——そのデータが正しいことを TxPipe を信頼してもらう方式だから、と本人が説明しました。
  • Mithril のスナップショット。TxPipe を信頼したくなければこちら。ただし Mithril のスナップショットは Cardano ノードの内部構造と強く結びついているので、Dolos はそのまま使えず、ブロックを最初から処理し直す。「少し余計に時間がかかる」。
  • 上流のピアから最初から引く。ノードと同じように、リレーからブロックを取ってくる。

「自分のリスクプロファイルと、いちばん筋の通るスナップショットを選べる」というのが Santiago のまとめです。

ここで司会が Mithril を推す立場を語ります。Foundation は機関と関わるので、法的に必須というほどではないにせよ、IT 認証やコンプライアンスを保つために信頼を最小化したスナップショットが重要になる場面がある。パートナーからも「そのスナップショットはどこから来て、誰が出したのか」と聞かれる、と。あわせて、Foundation の側でも「ごく近い将来」Midnight ノード向けの署名付きスナップショットを提供したい、と述べています。

Santiago はそれに応えて、Blockfrost チーム（彼らも自分たちの基盤に Dolos を使っている、とのこと）と、もう 1 つのチームの 3 者でスナップショットに共同で署名する準備をしていると明かしました。3 者のどれかを信頼できるなら使える、という設計です。もう 1 つのチームの名前は字幕では「link caps」と聞こえ、動画の中では説明されていません。

素朴な疑問 — 「trust me bro」で本番のノードを立ててよいのか？

補足以下はこちらで足した解説です。動画の発言ではありません。

その疑問は正しく、Santiago 自身がそう名付けているのは、そこを隠さないためです。スナップショットとは「誰かが同期し終えたデータのコピー」なので、その誰かが間違ったデータ（あるいは細工したデータ）を配っていたら、受け取った側は気づけません。

3 つの入り口は、信頼の相手が違う

  • TxPipe のスナップショット —— TxPipe を信頼する。速い
  • 共同署名のスナップショット（準備中）—— 3 者のうち 1 者でも信頼できればよい。1 社が単独で細工するのは難しくなる
  • Mithril —— Cardano の SPO たちがステークで署名した証明を信頼する。特定の会社を信頼しなくてよいが、Dolos では処理し直しが要る
  • リレーから最初から —— 自分のリレーを信頼する。いちばん遅い

外から見分ける方法

「そのスナップショットの正しさを、誰の署名で確かめられるか」を聞けば足ります。答えが「配布元の 1 社」なら trust me bro、「複数の会社」なら共同署名、「チェーン上のステーク」なら Mithril です。

この動画で示されたこと・示されなかったこと

共同署名は「準備中」で、時期は述べられていません。Mithril のスナップショットから Dolos を作り直すのにどれくらいかかるかは「少し余計に」とだけで、数字はありません。補足TxPipe の公式ドキュメントには、Mithril から mainnet を初期化するのに「20 時間未満」とあります（2026 年 9 月時点の記載）。

司会は最後に、SPO が Midnight に参加するときの登録のステップにも Dolos が「おそらく」使えるだろう、と述べています。まだ調べている途中、という言い方でした。

7. 仕組み — 判断は閾値、文章だけがモデル

言語モデルは入っているが、「アラートを出すか」は一度も決めない。

作ったものは「ヘッドレスのサービス」だと説明されました。公開のテレメトリのフィードを購読し、落ちれば systemd が再起動し、起動のたびにシークレットを取り直す。Stevan が「ほかより重要」と言った 2 点は次のとおりです。

  • 検知は決定論的。アラートを出すかどうか、どれだけ緊急かは固定の閾値が決める。言語モデルは入っているが、「その判断は決してモデルがしない」。
  • アラートは事実で、宛先がある。バリデータ名、責任のあるオペレーター名、ランブック（対応手順書）へのリンクが入り、オペレーターにメンションして Foundation の誰かにも CC する。原因も修正案も出さない。「このバリデータは報告を止めた」は事実で、「サーバーが落ちた」は物語。物語を入れると人はアラートを信じなくなる、と。

Stevan Lohja が「6 つのステップ」として説明した流れを描いたものです。動画ではスライドが映っていますが、この図はスライドを写したものではなく、音声の説明から組み立てています。

モデルは「同じマシンでセルフホストしている小さなオープンなモデル」で、事実を受け取って人間向けの 1 文を書く。ガードレールが、診断や対処の指示に読めるもの、メンション、注入（injection）の試みを弾く。そしてモデルが遅い・間違う・落ちているときは定型文でアラートが出る。「LLM が落ちても運用できていなければならない。どんなエージェント型サービスにも言えることで、標準的な考え方であってほしい」と述べられました。

運用面では、入ってくる経路がまったくない小さな VM が 1 台、ステータスページはループバックの裏、シークレットは起動時に取るので永続ディスクにも Terraform のステートファイルにも残らない、コンテナイメージはコンテンツハッシュで固定してあるので再起動で中身が静かに変わることはない、と挙げられています。

8. 検知ルールと費用

5 つのルール、2 段階の緊急度、月 56 ドル。

検知のルールは 5 つです。Stevan は「SRE や DevOps の面接で『気にすべき 5 つは何か』と聞いてきたが、これがその例」と言っています。

  • 不在（absent）—— 名簿にあるバリデータが消えた。デバウンス（連続確認）なし。「決して普通ではない」から
  • ファイナリティのギャップ—— 確定が遅れている。3 ブロックを超え、かつ 2 サイクル連続のときだけ発火
  • 同期中（syncing）
  • フォーク
  • ピア不足

後ろ 3 つは名前だけで、閾値は語られていません。数字の説明があったのはファイナリティのギャップだけで、1〜2 ブロックの再編成（reorg）は Substrate ベースのチェーンではごく普通、3 ブロックを超えたら Midnight では懸念すべきこと、という線引きです。補足Midnight のノードは Substrate（Polkadot 系のブロックチェーン開発フレームワーク）で作られている、と動画でも述べられています。

緊急度は 2 段階で、「5 段階の重大度の番号ではない」と強調されました。「今すぐ呼び出す」はコンセンサスが危険で誰かが起こされる。「通知」は朝に見ればいいもので、たとえばピアが 1〜2 つ足りないが動いている、といった状態。補足この 2 段階の説明の途中、38:44 から 40:00 までの約 75 秒は字幕が欠けています。

9. 本番で止めてみる — 認知まで 1 分

13 台のうち 1 台を stop し、スマホが鳴るまでを画面で見せた。

平均認知時間 mean time to acknowledgement、動画の中の言葉

問題が起きてから「ここに問題がある」と誰かが認知するまでの時間。Stevan は、重要度の高いものなら 5〜15 分が良いとされ、中程度なら 30 分〜2 時間、低ければ 5 時間以上、と「調べればいろいろ出てくる」相場を挙げたうえで、自分は全部 1 分以内にしたいと述べています。補足「復旧までの時間」（mean time to resolution）とは別の指標です。今回の実験で測ったのは前者で、復旧は Stevan が手で再起動しています。

Stevan は「悪いことをします」と言って、チェーン上の 13 ノードのうち Foundation の 1 台を systemctl で停止しました。1 回目は sudo を忘れて止まっておらず、やり直しています。時刻は東部時間 1 時 18 分。

時刻はいずれも Stevan Lohja が画面を見ながら読み上げたもので、米国東部時間です。通知の本文は「maintenance のコンセンサスのアラート、重大度は 1（critical）。Foundation のノードがネットワークから XYZ ブロック遅れている」と読み上げられ、遅れたブロック数は「XYZ」と伏せて読まれました。

通知は Stevan のスマホに届き、チャットのチャンネルには「バリデータがダウンしているという重大なイベント」が投稿され、Stevan ともう 1 人にタグが付き、ランブックが参照されていた、と読み上げられました。再起動すると「重大なインシデントは解決した」と追記され、その時刻が 1 時 20 分。「認知まで 1 分、次の 1 分で私がノードを再起動した」というまとめです。

このエージェントは本番に入って「2 週間ほど」で、何度か発火しているが「大したことではなく、どこかの計画メンテナンスなど」とのこと。効果として本人が挙げたのは指標ではなく、不安が減ったことでした。必要なときは必ず電話が鳴ると分かっているので、Grafana を見ていなければという不安を持たなくてよい、と。

このあと Stevan は、この構成を Terraform のテンプレートにして公開したい、そこにエージェントのツールも入れたい、と述べています。「初期段階」という言い方で、時期は語られていません。

In one line

Running a Midnight node means running a huge indexing database (db-sync) on the Cardano side. This session is about dropping that assumption.
Santiago Carmuega of TxPipe presents Dolos, a single-binary alternative, and the problem statement (MPS-0038) that asks Midnight to first specify exactly what it reads from Cardano. Then Stevan Lohja of the Midnight Foundation stops a production validator on purpose and shows his alerting agent paging him within a minute.

Key points

  • Midnight reads a thin slice of Cardano. UTXOs at a few addresses, pool stake, the chain nonces, the tip. “Probably measured in megabytes,” he said. Yet today that needs cardano-node, db-sync and PostgreSQL together: around 64 GB of RAM, 700 GB of disk and five to eight cores, by his account.
  • Dolos is one binary. About 3 GB of RAM and half a core. Chain history can be kept as a window (“a day, a week, a month”) with older records dropped. An SPO can point it at a relay they already run, so no second Cardano node next to it.
  • The ask is a boundary, not a swap. The problem statement filed the day before asks for a specified interface between the Midnight node and whatever reads Cardano, plus a conformance test suite. Only once that exists would a second proposal put Dolos through it.
  • Three ways to sync. A TxPipe snapshot (“trust me bro,” in his words), a rebuild from a Mithril snapshot, or pulling blocks from a relay from scratch. Snapshots co-signed with Blockfrost and a third team are being prepared, he said.
  • The alerting agent: thresholds decide, the model only writes. Five detection rules and two urgency tiers are fixed numbers; a language model turns the facts into one sentence, and a template sentence goes out if the model is down. $56 a month on GCP, with model inference at zero, he said.

2. What Midnight reads from Cardano, and what db-sync costs

Megabytes are needed. Seven hundred gigabytes are provisioned.

Santiago Carmuega starts from what a Midnight node actually reads from Cardano. Not everything that happens on Cardano, but a thin slice the consensus side needs. He names four things.

  • UTXOs in a particular script address
  • the stake that different pools have
  • the nonces of the chain
  • what the tip of the chain is

added Why Midnight reads Cardano at all is taken for granted in the video. Midnight is a Cardano partner chain, a separate chain that borrows Cardano's SPOs and stake: it uses Cardano's stake and nonces to decide who produces the next block, and reads registration data held at script addresses on Cardano. That is why the “thin slice” matters to consensus.

What operators are asked to run today to get that slice is cardano-db-sync, which pours the whole of Cardano into PostgreSQL and, in his words, is “self-described as a general-purpose indexer.” It serves explorers, wallets and exchange analytics, and to do so it stores everything. Running it takes three things.

  • a PostgreSQL instance
  • db-sync itself, the process that keeps writing into PostgreSQL
  • a Cardano node co-located with it

His rough total for the three: around 64 GB of RAM, 700 GB of disk, five to eight cores. On top of that, keeping it synced, keeping the parts playing together and tuning PostgreSQL is “many times a full-time job, in a sense.” The host adds his own experience: after db-sync finishes syncing you find you still have to re-index everything into Midnight's own database, and “this takes much longer than I needed to just to get the node up and running.”

Twice, Santiago says “this is not a critique on DB sync.” It is a great piece of software; the problem is the friction between what Midnight needs and what it provides.

The figures on the left are the ones Santiago Carmuega gave as “probably around”; the Dolos figures on the right are his too. added The problem statement MPS-0038, filed the day before, adds to the db-sync side: 700 GB of SSD with 60,000 IOPS, and about two days to sync mainnet.

added The RAM figure differs by source. MPS-0038 lists both: Midnight's own docs say 32 GB, the db-sync README recommends 64 GB. In the video Santiago uses 64. Neither the video nor the document settles which reflects real operation.

3. Dolos: a “data node” in one binary

No block production, no validation. A node that only reads.

Santiago calls Dolos a Cardano “data node,” and that term is used below.

Data node the speaker's term

“It's not a block producer, it's not validating blocks, it's not relaying the network.” It connects directly to the relay network, keeps its own copy of the ledger in an embedded database, and serves the query APIs from the same process. added A normal Cardano node both takes part in consensus and holds the data. Dolos splits off only the second role; TxPipe's own documentation states it “does not support block production and never will.”

Four features are called out in the video.

  • A “rainbow of APIs” in one process. An endpoint “that looks exactly like Blockfrost,” UTxO RPC (a gRPC API for UTXO chains), a Kupo-compatible interface, and Ogmios layered on top. “You can just be querying Dolos as if it were Blockfrost.”
  • A small footprint. About 3 GB of RAM; “you can be very comfortable with half a core.”
  • Truncated history. No need to keep everything from Byron. You pick a window (“a couple of days,” “six weeks”), it follows the tip, and older records are dropped. “For me the most interesting part.”

What “truncating history” means

Cardano's chain runs unbroken from 2017 (the Byron era) to today, and db-sync indexes all of it, hence 700 GB. Dolos lets you keep a fixed width, say the last day or the last six weeks, and delete what falls behind it. The video calls this a sliding window: the window moves with the tip.

Why a few days is enough for Midnight

“A couple of days if you care about the stability window,” he says. Cardano treats blocks older than a certain depth as settled, meaning they will not be rolled back; that depth is the stability window. Midnight wants recent, settled state, so as long as the window covers that depth, anything older need not be readable.

An everyday comparison

Keeping every back issue of a newspaper (db-sync) versus keeping this week's and recycling the rest (Dolos). If all you read is today's paper, the second is enough.

What the video does not say

The minimum width a Midnight node actually needs, and where “six weeks” comes from, are not explained. “I know Midnight does” care about the stability window is the whole of it, and he moves on.

Both speakers stress the use is not limited to Midnight. The host points out how many developers lean on the Blockfrost API; Santiago says “several teams” expose the Blockfrost API embedded in Dolos and “their production mainnet endpoints just hit” it. There are reasons to pay a service provider — high availability, edge distribution, dynamic scaling — but if you want to own your infrastructure and your use case permits, Dolos is “a really interesting alternative.” It is open source and takes contributions from multiple teams, he adds.

A fair question — is “trust me bro” acceptable for a production node?

The question is fair, and Santiago's nickname for the option is there precisely so nobody misses it. A snapshot is a copy of someone else's finished sync. If that someone shipped wrong or tampered data, the recipient cannot tell.

The three entry points trust different parties

  • TxPipe snapshot — trust TxPipe. Fast

6. The alerting agent: what the problem was

Nothing was broken. Nobody was watching.

The second half is Stevan Lohja following up on the alerting agent he described at the last Fireside Dev Hang. Then it was a plan; “it's now in production.”

It starts from one incident. Validator alerting “used to live in a browser tab,” Grafana and the like, posting to chat, fine at 11 in the morning “but useless at 3 a.m. on a Sunday.” On a test network, a finality stall went unnoticed because the last person with the telemetry open had closed their laptop and gone to bed. “Nothing was broken, but nobody was watching. And that's a problem.”

He lists four problems, “and only one of them is technical.”

  • Alerting only ran while someone had the metrics open
  • Off-hours cover was a human checking a page every 30 minutes or so; not everyone checks all the time
  • Midnight is currently a federated network with many parties to coordinate
  • Seeing a node name in telemetry is not the same as knowing who to call

He puts a number on the fourth: Midnight has 13 validators run by different organisations, “and the name on the screen doesn't tell you whose phone should ring.” Querying the blockchain will not tell you who can acknowledge and resolve a problem. added “13” is his figure as of 2 September 2026; the operating organisations are not named in the video.

7. Architecture: thresholds decide, the model only writes

There is a language model in the loop, but it never decides whether an alert fires.

What he built is “basically just a headless service.” It subscribes to the public telemetry feed, systemd restarts it if it dies, and it refetches its own secrets on every boot. The two things he says “matter more than the rest”:

  • Detection is deterministic. “Fixed thresholds decide whether an alert fires and how urgent it is. And there's a language model in this system, and I'll come to it, but it never makes that decision.”
  • The alert is factual and addressed. It names the validator, names the operator responsible, links to runbooks, mentions the operator and copies someone from the Foundation. It does not guess: no cause, no suggested fix. “This validator stopped reporting is a fact; their server crashed is a story. And if you put stories in alerts, people stop believing them.”

The flow Stevan Lohja described as “kind of six steps.” Slides are on screen in the video, but this figure is built from the spoken explanation, not copied from a slide.

The model is “just a small open model, self-hosted on the same box”; it “gets the facts and writes one human sentence or so.” Guardrails “reject anything that reads like a diagnosis or remediation instruction,” and reject mentions and injection attempts. If the model is slow, wrong or down, “the alert goes out with a template sentence instead.” His general point: “if your LLM goes down, you should still be operational. I hope it's like a standard practice philosophy.”

Operationally: one small VM with no inbound path at all, status pages behind loopback, secrets fetched at boot so they are never on persistent disk or in the Terraform state file, and a container image pinned by content hash “so a reboot can't quietly change what's running.”

8. Detection rules and cost

Five rules, two tiers, $56 a month.

There are five detection rules. He frames them as the answer he looks for when interviewing SRE and DevOps candidates about “five things that you're looking out for.”

  • Absent — a roster validator has vanished. No debounce at all, “because a roster validator vanishing is never normal”
  • Finality gap — fires above three blocks, but only after two consecutive cycles
  • Syncing
  • Fork
  • Low peers

The last three are named only; no thresholds are given. The one number explained is the finality gap: one- to two-block reorganisations are “very normal for Substrate-based chains, which is what Midnight is,” and above three “is usually cause for concern.” added The video itself states the Midnight node is built with the Substrate SDK, the Polkadot-lineage blockchain framework.

Urgency has two tiers, “not five severity numbers.” “Page now” means consensus is at risk and someone gets woken up. “Notify” is something to look at in the morning, such as a validator missing a peer or two but still running. added The captions have a gap of about 75 seconds, 38:44 to 40:00, in the middle of this explanation.

Cost is given as $56 a month, priced on GCP. The line he wants noticed is “model inference, which is zero,” because the model runs on CPU already paid for. Most of the bill is idle capacity kept so “your inference has somewhere to run.” “To be honest about it, a hosted model would be technically cents a month, and a paging platform starts around dollars per user,” so “maybe my solution is not the cheapest.” What it is, in his framing, is the version where the operational data and the operators “never leave our own projects.”

A fair question — if thresholds make every decision, why have a language model at all?

added What follows was written to help; it is not from the video.

The question is fair, and Stevan says as much: “the LLM actually just provides a better experience.” A design that falls back to a template sentence when the model is down has, by definition, made the model optional.

Why it is there anyway (as far as the video shows)

  • “Writes one human sentence” — turning a row of numbers into something an operator can read half-asleep
  • A door to “more capabilities” — the later ambitions (governance, hard-fork monitoring) would give the model more to do
  • It costs nothing extra — self-hosted, inference at zero; there is no bill to justify

How to tell from outside

Switch the model off and see whether alerts still arrive. If they do, the decision sits in the thresholds; if not, it depends on the model. By his account, the former.

What the video does not say

Neither the model's name nor its size is given, only “small open model” on CPU. How the guardrails actually judge a sentence, whether by pattern matching or another model, is not described either.

10. Where next: governance, hard forks

Once alerting is solid, point the same agent at wider things. All of it as ideas.

Prompted by the chat question (next section), Stevan sketches where the agent could go. Everything is “I think that'd be cool” or “theoretically,” not a decision.

  • Cardano governance. An agent that notices retired stake pools or inactive DReps and does “a wellness check”: “you're a retired pool, you're not doing anything, you have a lot of delegation, how's everything going?” Or watches governance proposals against their thresholds and nudges pools that have not voted. “Probably quite trivial”; the hard part is contacting the right people, and “coordination data” is what matters most.
  • Hard-fork monitoring. Midnight will hard fork “in the near future,” he says. With a large validator set it is hard to get everyone updated. When he ran hard forks in the Ethereum Classic ecosystem, they ran both the non-forked and forked chains in parallel to see who had not updated; an agent could spin that up with Terraform.
  • More raw node data. Scale the model up for more context and give it access to more information from the node as “the next phase.”

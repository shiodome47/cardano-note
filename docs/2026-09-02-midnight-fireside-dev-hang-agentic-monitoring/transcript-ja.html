00:04:09 — Midnight が Cardano から読むもの、そして db-sync の重さ

Santiago00:04:09

ご存じだと思いますが、Midnight を動かすには Cardano 側で起きていることを観測する必要があります。多くはありません。Cardano で起きること全部を追う必要はなく、Midnight のコンセンサス側で必要になるのは薄い一枚のデータです。特定のスクリプトアドレスにある UTXO、各プールのステーク、チェーンのノンス、チェーンの tip がどこか。小さなものですが、Midnight のコンセンサスにとっては本当に重要です。

Santiago00:04:55

そのために現状では、Midnight のオペレーターは db-sync を動かす必要があります。さっき言及されていたツールで、Cardano では有名です。チェーンのデータを探索するなら、これというツールです。フル機能の、非常に重量級のインデクサで、すべてを保存します。あらゆるトランザクション、あらゆる UTXO、ポリシー、アセット、DRep の投票、提案、すべてです。すばらしいのですが、汎用のインデクサです。自分たちでも「汎用インデクサ」と名乗っています。つまり、フル機能のエクスプローラを動かすにも、ウォレットにも、取引所のデータ分析にも使う、同じツールです。複数のユースケースに応えるという意味で、汎用に作られています。

Santiago00:05:55

問題は、リソースをたいへん食うことです。db-sync を動かすには、まず自前の PostgreSQL が要ります。次に、すべてを PostgreSQL に書き込む更新処理を行う db-sync 本体。さらに、db-sync と同じ場所に Cardano ノードも要ります。この 3 つを足し上げると、だいたい RAM が 64GB、ディスクが 700GB、CPU が 5〜8 コアです。本当に重くて、リソースを食います。それだけでなく、運用の面でも管理が複雑です。正しく同期しているか、各コンポーネントがうまく連携しているかを確かめ、必要な性能を出すために PostgreSQL をチューニングしなければならない。同期して、遅れないようにすることも、ある意味フルタイムの仕事になることが多い。要するに、本当に重いということです。

Santiago00:07:17

これは db-sync への批判ではありません。すばらしいソフトウェアです。ただ、Midnight が Cardano に求めるもの――Midnight が必要とするのは全部合わせてもギガバイトではなくメガバイトで測れるであろう薄い一枚――と、db-sync が提供するものと、それに必要なリソースの全部との間に、ある種の摩擦があるのが見えます。だから、代わりがあるかもしれない。別の種類の Cardano オブザーバー、もっと軽量で、Midnight ノードが必要とするものに合わせて要件を絞り込めるものがあるのではないか。そこで出てくるのが Dolos です。

00:08:04 — Dolos — 1 バイナリの Cardano「データノード」

Santiago00:08:04

Dolos は Cardano の「データノード」です。ブロック生成者ではなく、ブロックの検証もせず、ネットワークの中継もしません。やっているのは、リレーのネットワークに直接つないで、台帳の自分用のコピーを組み込みデータベースの中に保持することです。PostgreSQL はなく、何もありません。Dolos と並んで動くデータベースで、同じ 1 つのプロセスの中に、データを取り出すための API がひととおり入っています。Blockfrost とまったく同じ見た目のエンドポイントがあるので、Blockfrost に問い合わせるのと同じように Dolos に問い合わせられます。Dolos の上に Ogmios を載せて、Dolos 経由で Ogmios の API を使うこともできます。UTXO RPC もあります。UTXO 型ブロックチェーン向けの、gRPC ベースの非常に高性能な API です。これらの API がすべて同じプロセスに組み込まれています。

Santiago00:09:12

この 1 つのプロセスで、db-sync が要求する PostgreSQL、db-sync 本体、ノード、の 3 つを置き換えます。全部を 1 つのバイナリに詰めたことには、SPO の視点から見て面白い利点があります。SPO なら喜ぶだろうと思うものです。まず、リソースの消費量がずっと小さい。Dolos を動かすのに要るのは RAM 約 3GB で、64GB ではありません。CPU は 0.5 コアを割り当てれば十分快適です。

Santiago00:10:11

そしてディスクの面――私にとってはここがいちばん面白いのですが――チェーンの全履歴を保持する必要がないのです。Byron から今までの全部を保存する 700GB のディスクは要りません。チェーンの履歴を、スライディングウィンドウで持つことを選べます。チェーンが進むにつれて古いレコードを切り詰めて捨て、必要な分だけを残す。安定性ウィンドウ（stability window）が気になるなら数日分――Midnight はそうだと知っています。もう少し余裕を持って 6 週間前までロールバックできるようにしたいなら、それも可能です。設定で決められます。Dolos を立てるとき、このウィンドウをどれだけ持つかを決めると、そのウィンドウが tip に追随します。つまり、Midnight が求める薄い一枚のデータを提供するのに必要なディスク容量を、劇的に減らせます。

Santiago00:11:00

最後に、Cardano ノードは要ります。何らかの情報源を信頼する必要はある。ただ、db-sync が要求するように、インデクサと同じ場所に置いた Cardano ノードである必要はありません。Dolos をネットワーク上のリレーノードに向ければ、Cardano の P2P プロトコルの中でもう 1 つのノードであるかのように振る舞います。SPO なら、すでにリレーノードを動かしているはずです。自分のノードは当然信頼できるので、Dolos をそのリレーに向ければ、db-sync の隣にもう 1 つ Cardano ノードを置くという発想をまるごと省けます。全部足し合わせると、リソース使用量と運用の両方の最適化――面倒を見るバイナリが 1 つだけになる――は、SPO の運用の視点から歓迎されるものだと思います。

Stevan00:12:01

いいですね。おっしゃったとおり、多くの SPO はすでに Cardano のリレーを持っています。本番の SPO なら、たいてい 2 つ以上のリレーがある。Midnight のバリデータになるなら、64GB より 3GB の RAM を用意するほうがずっと簡単です。これは大きい。本番で動かしている SPO は、たいてい少し余裕を持たせていますが、想定より 64GB 多い、ということはまずないでしょう。

Stevan00:12:43

ええ、まさにそうです。あのインデックス作成のステップにやられる。私も毎回やられます。私たちはやっていることの都合で、db-sync のインスタンスをたくさん動かしています。繰り返しますが、これは db-sync を叩く記事ではありません。すばらしいソフトウェアです。ただ本当に重量級で、特定のユースケースでは理にかなっている。Midnight が必要とするものに対しては、もっと適した選択肢があると、私はかなり確信しています。だからこそ私たちは――すみません。

Stevan00:14:13

それと、Cardano エコシステム全体に対する一般的な解決策としても、大きな価値がありますよね。Blockfrost の API に頼っている人も多く、かなり人気があります。これは、そういう人たちも使えるものです。

Santiago00:14:33

ええ、そのとおりです。開発用途では本当に面白い。1 つのプロセスで、非常に軽量で、開発、テスト、ストレステスト、DApp の実行に使えます。それに加えて、いくつかのチームは Dolos の Blockfrost API を外部に公開し、本番の mainnet のエンドポイントが Dolos に組み込まれたその Blockfrost API を直接叩いています。そうやって自分たちのインフラを自分で持てる。サービスプロバイダーにお金を払うほうがよいユースケースもあります。高可用性、エッジへの分散、動的なスケーリング。サービスプロバイダーを選ぶ理由はある。一方で、ユースケースが許すなら、自分のインデクサ、自分のインフラを持ちたい理由もあって、Dolos は本当に面白い選択肢です。DApp のバックエンドの問題に向き合っている方には、ぜひ試してみてほしい。

Santiago00:16:52

断っておくと、私は MPS と MIPs のプロセスは初めてで、これが最初の 1 本です。ただ、とても理にかなったプロセスだと思います。まず問題提起から始める。解決策の変更とは無関係に、何が改善できると思うかを述べるだけで、どう改善するかは言わない。それが問題提起で、昨日投稿したものです。ほんの少し前にマージされたと思います。チームの速さを物語っていて、すばらしい。そこで述べているのは、今説明したとおり、db-sync は特定のユースケースではすばらしいが、Midnight のノードを動かす文脈では少し過剰かもしれない、ということです。提案しているのは、それを Dolos に置き換えることではありません。むしろ逆で、問題提起では解決策の話はしていない。言っているのは、Midnight ノードと「Cardano オブザーバー」が何であれ、その間のインターフェースを記述する、明確な契約――きちんと定義された仕様――があるべきだ、ということです。その境界をきちんと定義し、どのオブザーバーのバックエンドでも要求事項をすべて満たしているかを確かめられる適合テスト（conformance test）のスイートがあれば、「この SPO は db-sync の代わりに別の解を動かしたい」と考え始められる。それは Dolos かもしれないし、ほかにも適したバックエンドがあるかもしれない。問題提起が求めているのは、厳密な境界と明確に定義されたインターフェースで、ベンダーが入ってきて自分のバックエンドを提供できるようにすることです。それが承認されたら――まだドラフトですが――後半にあたる改善提案を出します。そこでは「このインターフェースができたので、db-sync の代わりに Dolos を使ってみてはどうか」と提案し、プロトコルの視点から要求される適合テストをすべて満たす努力をします。
